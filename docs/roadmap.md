# 개발 로드맵

단계별 목표와 다음 단계로 넘어가기 위한 조건입니다. 실제 운영 완료 여부는 검증 결과로 판정합니다.

| 순서 | 단계 | 산출물과 완료 기준 |
| --- | --- | --- |
| 1 | 기반 · P1-A | Desktop·Telegram 요청을 동일 작업 모델로 처리하고 접수, 상태, 승인, 예산의 연결을 확인 |
| 2 | P1-C A · 안정화 | 접수와 비동기 처리의 식별자 일치, 비활성 Swap 차단, 예산 조회 인증과 기존 기록의 무결성을 검증 |
| 3 | P1-C B · 계획 검증 | 격리 프로젝트에서 Fixed와 Swap 계획을 각각 생성해 역할, 승인 SHA, 예산, 승인 대기 상태를 확인. 모델 호출과 프로젝트 파일 변경은 0건 |
| 4 | P1-C C · 실제 협업 검증 | 사용량 한도와 별도 실행 승인을 확인한 뒤 선택한 격리 작업의 모델 호출, 독립 검증, 패치 적용 또는 복구를 확인 |
| 5 | P1-B · 알림 통합 | Desktop에서 시작한 작업의 승인 대기·완료·실패를 권한 있는 Telegram 수신자에게 전달하고 중복을 제어 |
| 6 | 운영 안정성 및 지식 관리 | Desktop 세션과 Gateway 수명 주기의 분리 검증, 중단·재개 회귀 테스트, 승인 기반 공동 기록 갱신 및 백업 복원 검증 |

P1-C B는 계획과 실행 경계의 검증입니다. P1-C C의 실제 호출 승인은 별도로 받으며, 승인 대상 외 계획은 대기 상태로 유지합니다. 상세한 판단 기준은 [테스트 전략](testing-strategy.md)을 참고합니다.
